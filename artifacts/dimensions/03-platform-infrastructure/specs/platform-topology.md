## Executive Summary

This document defines the platform storage topology for the Global Transaction Banking data model. It evaluates two architectural options against confirmed workload requirements and volume constraints, then recommends a path forward with full synchronization architecture between stores.

### Volume Constraints (Confirmed — Phase 1 Scale Envelope)
| Parameter | Value | Derived Total |
|-----------|-------|---------------|
| Top-level entities (~Legal Entities/Parties) | ~10,000 | baseline |
| Sub-entities per entity (branches/departments/divisions) | up to 20 | ~300K nodes max |
| Products per entity | ~10 | includes cash pool + lending + FX hedging etc. |
| Virtual accounts within single cash pool | ~100 each | primary deep-nesting driver |
| **Estimated peak node/record count** (graph + relational combined) | — | **~5–8M total across all stores** |

### Workload Tiers & Latency Requirements
| Tier | Use Case Examples | SLA Target | Store Implication |
|------|------------------|------------|-------------------|
| **Real-time operational** | Entitlement validation, ownership traversal, mandate scope check | < 5ms p99 | Graph-native traversal or indexed lookup on hot data set |
| **Near-real time stateful** | Account balances (up-to-second), client statement rendering, cash position dashboards | < 1s refresh precision | Relational/Time-Series with CDC or synchronous dual-write |
| **Governance & analytics projections** | Cross-LOB KPI computation, regulatory exposure sweeps, historical point-in-time queries | Hourly to daily is acceptable | Databricks/Delta Lake batch + CDF pipelines; time-travel on demand for ad-hoc PIT analysis |

### Core Invariant (Reaffirmed)
> **The graph IS the canonical model of relationship in GTB.**  
> Operational databases are read-optimized projections shaped by LOB exposure and organizational structure. Materialisation is always derived from — never source to — the graph.

## Option A: Three-Specialized Stores

### Architecture Overview

```
┌───────────────┐     ┌──────────────────┐     ┌──────────────────────┐
│   Neo4j       │ CDC │  PostgreSQL /    │ CDF/ │   Databricks +       │
│ (Canonical)   │ ──▶ │  TimescaleDB     │ Batch│   Delta Lake         │
│               │     │  (Relational      │─────▶│   Unity Catalog      │
│ • Entity-     │     │    Projection)   │     │                     │
│   Relationship│◀─── │                 │     │ • tb_canonical       │
│   Graph        │ sync│ • Account State │     │ • LOB projections  │
│ • Entitlements│     │ • Balances/State │     │ • Analytics + KPIs   │
│ • Mandates    │     │ • Statement Data │     │ • Temporal History   │
└───────┬───────┘     └────────┬─────────┘     └──────────┬───────────┘
        │                      │                          │
        └──────────┬──────────┴──────────────────────────┘
                   ▼
            Entity Platform API
         (REST façade; consumers never touch stores directly)
```

### Store Roles & Data Distribution

| Layer | Technology | What Lives Here | Volume Estimate | Why Not Elsewhere |
|-------|-----------|-----------------|-----------------|-------------------|
| **Canonical Graph** | Neo4j Aura DB or self-managed cluster | Entity nodes (Party, Group), relationship edges (owns-controls-operates-within), mandate hierarchy trees, entitlement graph paths | ~300–500K nodes + 1M+ relationships after deep nesting | Native multi-hop traversal (<5ms); recursive CTEs on Postgres degrade past depth-4; Delta Lake not built for operational sub-second queries |
| **Relational Projection** | PostgreSQL with TimescaleDB extension (or vanilla PG if time-series needs are light) | Account balances, virtual account state, cash pool snapshots, transaction-ledger rows, statement-ready materialized views | ~5–7M records at peak (driven by 10K entities × 10 products × 100 VA per pool = worst case ~10M but most pools won't hit max) | ACID transactions for balance precision; sub-second CDC refresh from graph events; columnar projections not needed here since queries target specific accounts/time-ranges, not full-scan analytics |
| **Governance + Analytics** | Databricks on Azure (Delta Lake tables under Unity Catalog `tb_canonical`) | Full temporal history of entity state changes, proof chain summaries, cross-LOB KPI aggregates, regulatory exposure snapshots, ad-hoc PIT query base via Delta time-travel | Grows over time; ~10–20M rows/year with append-only CDF pattern; partitioned by date + domain scope | Batch/analytics bias is fine here — no sub-second SLA. Unity Catalog provides row-level security and column masking for regulated data without app-layer complexity |

### Synchronization Architecture (Option A)

#### Direction: Graph → Relational Projection
```
Neo4j Events  ──CDC──▶  Kafka / Event Hub Topic  ──consumer──▶  PostgreSQL Write
  
              [relationship.created]                [INSERT INTO accounts...]  
              [entity.updated]                      [UPDATE balances SET ...] 
              [entitlement.revoked]                 [REVOKE FROM role_lob_x;]
```

**Mechanism:** Lightweight change-data-capture from Neo4j via one of:
- **Neo4j Connector for Kafka / Azure Event Hubs** — native streaming plugin that emits graph mutations as structured events (node-id, type, properties-diff, timestamp) to topic per domain (`entities`, `relationships`, `entitlements`)
- **Change Log Poller Service** — thin custom microservice polling Neo4j's transaction log at configurable interval; converts Cypher-level mutations into relational INSERT/UPDATE statements via prepared SQL batches

**Refresh cadence target:** Sub-second CDC for balance-critical paths (account state changes). Non-balance attributes can batch to 5–10s window. At ~300K node scale, both approaches are well within capacity — no heavy stream processing needed.

#### Direction: Relational + Graph → Databricks Delta Lake
```
PostgreSQL WAL / Neo4j Export  ──nightly or hourly──▶  Azure Data Factory Pipeline  
                                                   │                                       
                                             Unity Catalog tb_canonical 
                                          (append-only tables with CDF enabled)
                                                     │
                                            LOB catalogs granted SELECT + RLS via domain_scope ARRAY<STRING> filtering per caller_lob context
```

**Mechanism:** Standard batch ingestion pipeline. At this scale, full table sync or incremental append from CDC log is trivial — no complex stream topology needed. Delta Lake's time-travel capability means historical point-in-time queries don't need separate archival store; just query with `TIMESTAMP AS OF '{iso-timestamp}'` syntax.

### Advantages (Option A)
| Benefit | Impact |
|---------|--------|
| **Optimal per-workload** — each store is purpose-built for its tier's access pattern and SLA | Eliminates compromise; graph stays fast, balances stay precise, analytics don't block operational queries |
| **Clear separation of concerns** — team ownership maps naturally: platform owns graph, LOB teams own relational projection tuning, data engineering owns Delta pipelines | Reduces cross-team merge conflicts and deployment coupling |
| **Regulatory narrative is clean** — immutable append-only ledger (QLDB or Delta CDF) for proof chain + Unity Catalog governance plane already locked as decision in Dim 02 | Easy to demonstrate compliance posture during audit; temporal history always available via time-travel without impacting operational DBs |

### Disadvantages & Mitigations
| Drawback | Risk Level | Mitigation |
|----------|-----------|------------|
| **Operational complexity** — three platforms to provision, monitor, back up, patch | 🟠 Medium at ~10K entity scale; becomes material cost past 50–100K entities | Start lean: Neo4j Aura DB (managed), single PostgreSQL instance on Azure Database for PostgreSQL, Databricks workspace already exists. Total infra overhead is manageable with platform team of 2–3 engineers |
| **Data consistency across stores** — eventual consistency window between graph and relational projection could cause stale reads if not bounded tightly | 🔴 Critical if balance queries hit during sync gap | Keep CDC lag <5s via event-driven pipeline (not polling). Add version/timestamp column on every row in PG so application layer can detect staleness before rendering. For sub-second SLA use cases, add synchronous dual-write fallback for hot path mutations only (~10% of writes that directly affect account state) |
| **Cost** — three managed services vs one | 🟡 ~$3–5K/month estimated run-rate at this scale (Neo4j Aura Standard + Azure PostgreSQL Business Critical 8 vCores + Databricks DBU consumption). Verify with actual pricing calculator before procurement | Consider consolidating to Option B if budget is tight and graph traversal depth stays shallow (<2 hops) for Phase 1 use cases; can migrate later as complexity grows organically |

## Option B: Single Operational Store (Simplified Topology)

### Architecture Overview
```
┌───────────────────────┐       ┌──────────────────────┐
│                       │ CDC/  │   Databricks +        │
│     PostgreSQL         │ Batch▶│    Delta Lake         │
│  (+ Apache AGE plugin) │─────▶│  (Unity Catalog)      │
│                        │      │                      │
│ • Entity nodes via     │      │ • Analytics only     │
│   AGE graph tables     │      │ • Temporal history   │  
│ • Relationships as     │      │ • LOB projections    │ 
│   directed edges       │      └──────────────────────┘ 
│ • Account state/balances│
│ • Entitlements/mandates │
└─────────┬───────────────┘          
          │                          
  Entity Platform API (REST façade; consumers never touch DB directly)
```

### What Changes vs Option A?

| Aspect | Before (Option A) | After (Option B — Single Store) |
|--------|------------------|---------------------------------|
| Graph store technology | Neo4j dedicated cluster → Apache AGE extension on PostgreSQL or recursive CTEs for shallow traversals (<2 hops); eliminates one managed service and its operational overhead entirely |
| Relational projection layer | Same PostgreSQL instance that also holds graph data — no separate sync pipeline needed; account state lives alongside entity relationships in same database with normal foreign key constraints enforced at schema level, zero eventual consistency window since everything is transactionally atomic within single ACID boundary |
| Synchronization complexity | Graph → PG CDC stream + error handling eliminated entirely (no cross-store replication to manage) | 
| Databricks pipeline | Unchanged — still batch/CDF ingest from PostgreSQL source via standard WAL or logical decoding connector; Unity Catalog governance plane stays exactly the same with `tb_canonical` and LOB read-projection catalogs using domain_scope RLS filtering just like Option A |

### Performance Profile (Option B at ~10K entity scale)
| Workload | Expected Latency | Notes |
|----------|-----------------|-------|
| Single-hop relationship query (`/entities/{id}/relationships`) — simple indexed join on edges table with type/state filter | < 5ms ✅ meets SLA comfortably for most single-parent-child lookups at this data scale; PostgreSQL index-only scans handle it well even without native graph engine | 
| Multi-hop traversal (ownership chain depth-3+, beneficial owner path-finding, regulatory exposure fan-out across nested subsidiaries) — recursive CTE or AGE `cypher()` query on 500K+ node/edge dataset with complex WHERE filters and multiple JOINs | **10–200ms ⚠️ borderline to miss SLA** depending heavily on traversal depth, index coverage strategy (GIN indexes help but don't match Neo4j's native adjacency list), concurrent query load under peak traffic; gets worse as entity graph deepens past 3 hops and fan-out exceeds ~5 edges per node average |
| Account balance lookup — direct indexed primary key or unique constraint scan on accounts table with partition by time for fast range queries if TimescaleDB enabled, otherwise standard B-tree indexes work fine at <10M row scale | < 2ms ✅ excellent; this is what Postgres does best and will easily meet sub-second SLA even under heavy concurrent read load from multiple LOB consumers hitting statement generation endpoints simultaneously |

### Advantages (Option B)
| Benefit | Impact |
|---------|--------|
| **Simpler operations** — one database to provision, monitor, back up instead of two separate platforms with their own patching schedules and failure modes; reduces team skill requirements from "Neo4j + Postgres" down to just PostgreSQL expertise which most banking platform teams already have | 
| **Zero cross-store consistency risk** — graph mutations and account state updates happen in same transaction so there's no eventual-consistency window between entity relationships and balance data that could cause incorrect statements or stale entitlement checks during sync gaps; eliminates entire class of bugs related to dual-write coordination and CDC lag detection logic at the application layer |
| **Lower cost, faster time-to-value** — removes Neo4j licensing/managed service fees (~$1–2K/month savings on Aura Standard tier); can ship Phase 1 MVP ~4-6 weeks sooner since team doesn't need to learn graph database administration or architect synchronization pipelines; just standard PostgreSQL schema design and API development |

### Disadvantages & Mitigations
| Drawback | Risk Level | Mitigation |
|----------|-----------|------------|
| **Graph traversal performance** — recursive CTEs on Postgres degrade past depth-3–4 hops even with good indexes; AGE plugin helps but doesn't match native Neo4j adjacency list optimization for deep path-finding queries needed by regulatory exposure analysis and beneficial ownership chain validation | 🔴 High if Phase 1 use cases require >2-hop traversals across the entity graph as a core happy-path operation (not just edge case). This is likely to become material pain point once corporate group structures exceed ~5 levels of nesting which many multinational clients already do per Nexus Global reference architecture pattern documented in Dim 01 |
| **Query complexity** — mixing Cypher-style path queries with relational SQL joins creates awkward developer experience and harder-to-optimize execution plans; PostgreSQL query planner isn't designed for graph-first thinking so even simple "find all subsidiaries owned by entity X through any chain of intermediate holding companies" becomes verbose recursive CTE that's hard to read, debug during perf issues, or explain to business stakeholders who think in terms of ownership trees not SQL | 🟡 Medium — acceptable for small team building MVP quickly but will slow down feature velocity as graph semantics grow more complex beyond simple parent-child containment; code reviews become harder and onboarding new engineers takes longer without clear mental model separating "graph queries" from "relational lookups" in same codebase |
| **Migration debt** — if you later discover Neo4j is needed for real-world multi-hop traversal performance under production load, migrating from PostgreSQL + AGE to dedicated graph database requires full data export/import plus application-layer refactor of all entity relationship query endpoints; this isn't a simple schema change but rather re-architecting how the Entity Platform API talks to its underlying store which could take 4–6 weeks of dev work during peak delivery when you'd prefer to be shipping new features not doing platform migration | 🔴 High — one-way door decision with significant rework cost; much easier architecturally and operationally to start with Neo4j than to add it later after team has already built all entity queries around Postgres recursive CTEs or AGE `cypher()` calls embedded in their service layer codebase |

## Recommendation & Rationale

### Recommended: Option A (Three-Specialized Stores) for Phase 1

**Why:** The graph-as-canonical-relationship-model invariant is non-negotiable per Dim 01 ontology design. At ~5–8M records across all stores, the operational overhead of three managed services on Azure remains reasonable (~$3–5K/month estimated run-rate). More importantly: **starting with Neo4j avoids migration debt** that would be expensive to undo later if Phase 1 reveals deeper traversal needs (>2 hops) under real client data patterns.

### When Option B Makes Sense Instead
- Budget is absolutely constrained and graph depth stays shallow (<2-hop traversals sufficient for all Phase 1 use cases like simple parent-child ownership without complex multi-tier holding company structures)
- Team has zero Neo4j experience AND cannot absorb learning curve within Phase 1 timeline (6–8 weeks to first customer demo or UAT sign-off deadline)  
- Willingness to accept potential re-platform migration cost (~$50K+ in engineering time if graph queries become bottleneck mid-delivery and you need to bolt on Neo4j retrospectively after already shipping Postgres-based entity service endpoints to LOB consumers who are depending on them for production statements or regulatory reporting)

**Bottom line:** Option A is the right architectural choice. Option B exists as documented fallback only if business constraints force it — not because it's technically superior, but because it ships faster with known skills when budget absolutely cannot support third managed service during MVP validation phase.

## Synchronization Layer Detail (Option A)

### CDC Pipeline: Neo4j → PostgreSQL
```yaml
pipeline-name: graph-to-relational-cdc  
source: neo4j-aura-db  
connector-type: kafka-connect-neo4j-plugin  # or custom poller service if Kafka not available in env  
topics: 
  - entities        # node create/update/delete events from entity.* labels  
  - relationships   # relationship create/type-change/delete across all edge types defined in Dim 01
  - entitlements    # authority grant/revoke scope changes affecting access control decisions at API layer  

consumer-service: relational-projection-writer  
target-database: azure-postgresql-primary   
write-pattern: prepared-statement-batch (batch-size=500, flush-interval=2s)

latency-target: < 5 seconds p99 end-to-end from graph mutation to PG row visible
error-handling: dead-letter-topic with manual retry UI + alert if queue depth > 10K messages for more than 60 seconds (indicates schema mismatch or downstream DB connection pool exhaustion requiring immediate platform team investigation)

consistency-guarantee: eventually-consistent within bounded lag window; application layer should check row-level version timestamp before rendering balance data to client-facing statement UI so stale reads are detected and either retried automatically or surfaced as "data refreshing" loading state rather than showing potentially incorrect figures from pre-sync snapshot
```

### Batch Pipeline: PostgreSQL + Neo4j → Databricks Delta Lake
This stays exactly the same regardless of which option you choose since Unity Catalog governance plane is already locked decision per Dim 02 memory log. The pipeline just reads from whichever source holds canonical operational data (graph or relational) and writes append-only tables to `tb_canonical` with CDF enabled for temporal queries plus LOB read-projection catalogs using domain_scope RLS filtering pattern that was explicitly defined during impact analysis phase last week when we mapped out 31-step DDL execution order.
